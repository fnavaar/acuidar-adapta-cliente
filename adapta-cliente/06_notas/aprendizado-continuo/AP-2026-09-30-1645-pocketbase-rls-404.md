# AP-2026-09-30-1645 — Comportamento de RLS no PocketBase: negação retorna 404

- Status: candidato
- Escopo: projeto do cliente
- Task/SPEC: F1-T04 · SPEC-1-002 (CA-1-10)
- Sinal: em coleções PocketBase, uma updateRule que nega não retorna HTTP 403 — retorna 404 ("The requested resource wasn't found"), porque o registro fica invisível ao perfil sem permissão. deleteRule null deixa exclusão somente para superusers; registros de teste criados via API autenticada não podem ser removidos sem superuser.
- Evidência: provas 2 e RV-2 (PATCH negado → 404) e provas 5 e RV-5 (DELETE → 403 "Only superusers can perform this action") no Skip 51740, versão 0.0.5; revalidação independente reproduziu o comportamento.
- Regra reutilizável: em testes de RLS no PocketBase, tratar 404 em PATCH/GET como negação efetiva (registro invisível), não como bug; a UI da leva técnica deve mapear 404 em edição → "sem permissão para este registro"; criar fixtures de limpeza em migration (contexto superuser) para não reter dados de teste na base.
- Quando aplicar: qualquer task que implemente ou teste regras de acesso (RLS) na intranet, e a UI de revisão/aprovação da leva técnica.
- Quando não aplicar: endpoints custom em hooks — o hook de recuperação (F1-T06) responde 200 com resultado explícito, fora do escopo das regras de coleção.
- Confiança: alta — comportamento observado duas vezes (prova original e revalidação do zero).
- Privacidade: sem segredo, dado pessoal ou conteúdo bruto.
